# VPS対戦システム移行 設計書

日付: 2026-07-12
ブランチ: `feature/vps-realtime-battle`
ステータス: 承認済み

## 1. 背景と目的

現在のCompileアプリはビルドツールなしのバニラJS構成で、GitHub Pagesから配信されている。マルチプレイヤーは2系統が併存する:

1. **Firebase Realtime Database版** (`room-play.html`) — クライアント信頼型のレガシー実装
2. **Supabase Edge Function + Postgres版** (`secure-room`) — サーバー権威型だが、通信は1.3秒間隔のHTTPポーリング

これを **自前VPS上のWebSocket（双方向通信）対戦システムに完全置き換え**、あわせてコードベースをフル近代化する。

### 決定事項（ヒアリング結果）

| 項目 | 決定 |
|---|---|
| 既存マルチプレイヤー実装 | Firebase版・Supabase版とも**廃止**、VPS一本化 |
| インフラ | VPS契約済み・ドメインあり（TLSはCaddyで自動取得） |
| リファクタリング度 | フル近代化（モノレポ + TypeScript + Vite） |
| UIフレームワーク | React |
| アカウント | アカウント制導入。範囲は**認証 + 戦績**（レーティングは将来） |
| マッチング | 従来通りルームコード + ロビー（自動マッチングなし） |
| React移植範囲 | ルーム対戦 + CPU対戦（盤面UI共有）。ソロプレイ・カード一覧・トラッカーは静的のまま配信し後続フェーズで移植 |
| サーバー技術 | Node.js + Fastify + Socket.IO |
| DB | MySQL + Drizzle ORM |

## 2. 全体アーキテクチャ

```
compile-app/ (pnpm workspaces)
├── packages/
│   ├── engine/      # 既存engine.js + data/cards.json + data/effects.json をパッケージ化
│   │                #   実績あるJSのまま変更しない。手書き型定義(index.d.ts)を付与
│   │                #   既存 test/engine.test.js をVitestへ移設
│   └── protocol/    # client/server共有のTS型とzodスキーマ
│                    #   Socket.IOイベント型、BoardView型（隠蔽済みビュー）と射影関数、REST DTO
├── apps/
│   ├── server/      # Fastify(REST: 認証・戦績) + Socket.IO(対戦) + Drizzle(MySQL)
│   └── web/         # Vite + React + TS（盤面UI: CPU戦 + ルーム対戦）
├── static/          # solo-play.html / cardlist.html / control-tracker.html を当面そのまま配信
└── deploy/          # Docker Compose定義・Caddyfile・CI/CD
```

### 設計原則

- **エンジンは聖域**: `engine.js` は純粋関数API・シード付き決定的乱数という優れた設計が既にあり、テストも存在する。JSのまま共有パッケージ化し、型定義だけ与える。書き換えない。唯一の例外として、`ruleset_version` をルール実行コードのハッシュから導出するため（3.1参照）、AI節（`Engine.ai`）を**ロジック無変更で別ファイルへ分離**する。ただしこれは**単純なファイル移動では成立しない** — AI節はクロージャ内部の関数・変数に直接依存する（`apply` の直接呼び出し: `engine.js:2459`、`TRACE` の直接書き換え: `engine.js:2465`、ほか `legalActions`・`DEFS`・`lineTotal`・`cardValue` 等）。分離方式は**内部APIエクスポート + 依存性注入**とする: ルール部ファイルの末尾（クロージャ内）にAIモジュール専用の内部APIオブジェクト（AI節が参照する関数群と、`TRACE` の読み書きアクセサ）を追加し、AIファイルはこれを受け取って自身の関数を構成、組み立てモジュールが従来と同一の公開API形状（`Engine.ai.*`）へ合成する。AI節の各関数のロジック自体は無変更で、分離の等価性は既存テストの全通過で検証する。
- **サーバー権威型を継承**: secure-room Edge Functionで確立済みの「サーバーでエンジン実行 → 合法手検証 → 相手の非公開情報を隠蔽したビューだけ配信」という設計をWebSocketに移植する。
- **ビューの隠蔽はサーバーの責務**: 相手の手札・デッキ・裏向きカード定義はサーバーから出ない。ただし現行 `index.ts` の別名生成は**そのまま移植しない**（下記3.2参照。現行方式には裏向きカードの正体を推測できる脆弱性がある）。

## 3. 対戦サーバー設計

### 3.1 ゲームセッション管理

- 進行中ゲームはメモリ上の `Map<roomId, GameSession>` で保持。
- 全アクションは `game_actions` テーブルへ追記し、**DBのログを正とする**（詳細は3.3）。
- エンジンは決定的なので、**ゲーム初期条件 + アクション列のリプレイで状態を完全復元可能**。サーバー再起動時は進行中ルームをDBから復元する。
- リプレイ復元の成立条件として、`games` に**不変のゲーム初期条件を保存する**:
  - `game_config`（JSON）: 両者のプロトコル3つ（`p0`/`p1`）、`seed`、`first`（先手）、`useControl` 等、`Engine.newGame()` に渡した引数の完全な記録
  - `ruleset_version`: **ルール実行コードのハッシュ + `cards.json`/`effects.json` の内容ハッシュ**から機械的に導出する。前提として、`packages/engine` 化の際に `engine.js` のAI節（評価関数・探索。`engine.js:1918` 以降の連続ブロック。ルール部はAI節を参照しないが、AI節はルール部の内部関数・`TRACE` に依存するため、分離は内部APIエクスポートを介した依存性注入で行う — §2設計原則）を**ロジック無変更で別ファイルへ分離**する。**ハッシュ対象は「分離後のルール部ファイル（内部APIエクスポート部を含む）+ `cards.json`/`effects.json`」**で、AIファイル・組み立てモジュールは含めない（内部APIエクスポートはAI調整では変更されない）。これによりAI評価ロジックの頻繁な調整ではバージョンが変わらず（リプレイはログ済みアクションを再生するだけでAIを呼ばない）、ルール実行コードの変更は**漏れなく自動で**バージョンに反映される — 手動バージョン定数では「代表ケースを通らないルール変更で更新を忘れる」故障モードが残るため採用しない。副作用として、ルール実行ファイルへのコメント等の無害な変更でもバージョンが変わるが、ルール部の変更は稀でありデプロイ時のドレイン手順（§6）で吸収する。バージョン不一致の進行中ゲームは現行コードでリプレイせず、無効試合として終了処理する（`status='void'`, `end_reason='ruleset_mismatch'`。頻度は低い想定なのでスナップショット互換層は作らない = YAGNI）。ただしこのvoid書き込みは起動直後には行わず、**§6起動バリアの段3（keep/rollback判定を通過し新app採用が確定した後、Socket受付開始の前）まで遅延**する — 起動時に即書き込むと、ヘルスチェック不合格で旧イメージへロールバックした際に、旧appなら続行できたゲームがvoid済みになる取り消し不能な事故になる。ルール変更を含むデプロイは進行中ゲーム0件のドレインを必須とする（§6）ため、この処理はドレイン漏れに対する安全網である。ゴールデンテスト（§8）は「意図しないルール挙動の変化」を検出する挙動レベルの安全網として併用する
- 現行の楽観ロック方式を踏襲: 各ビューにバージョン番号を付け、クライアントのアクションはバージョン一致時のみ受理。

### 3.2 カードIDの隠蔽（不透明ID・可視性エポック）

現行Edge Functionの別名生成（内部UIDのソート順に `c0, c1...` を割当）は**移植しない**。内部UIDは `p{side}:{カード定義ID}` 形式（`engine.js:1896`）で、プロトコル構成とカードデータが公開情報である以上、クライアント側で別名→UID→カード定義の対応を完全に再現でき、`def: null` にしても裏向きカードの正体が推測可能なため。

新設計:

- ゲーム開始時に暗号学的乱数で**ゲームごとの秘密値** `card_id_secret` を生成し `games` に保存。
- 公開ID = `HMAC-SHA256(card_id_secret, セッション互換ハッシュ + ":" + 内部UID + ":" + 可視性エポック)` の**先頭16バイト（128bit）**を base64url 化した不透明ID（セッション互換ハッシュは本節末尾で定義）。内部UIDの辞書順・カード定義から一切導出できない。
- **可視性エポック（ゲーム内不変のIDでは追跡漏えいが残るため）**: トラッシュのカードは定義つきで公開されるが、デッキ切れ時にデッキへシャッフルで戻り（`engine.js:586`。効果由来は `engine.js:1068`）、トラッシュ・場のカードが手札へ移る効果もある。IDがゲーム内で不変だと、正体が公開されていた時点のIDを後の裏向き登場と突き合わせてカードを追跡できてしまう。そこでカードごとにエポック（0起点のカウンタ）を持ち、**非公開ゾーン（デッキ・いずれかの手札）を経由したカード**のIDを更新（+1）する。次の遷移が対象:
  1. カードが**デッキへ入った**とき（トラッシュからの再構成シャッフルを含む）
  2. カードが**手札へ入った**とき（相手からは手札内容が見えないため、後で裏向きに再登場すると追跡され得る）

  **判定はアクション内の実ゾーン遷移で行う（前後差分では不足、滞在検出では過剰）**: 同一 `apply` 内で「トラッシュ→デッキ（シャッフル）→デッキトップから場へ裏向きプレイ」（`engine.js:1068`→`engine.js:1631`/`1647`）のように、非公開ゾーンを経由して公開領域へ戻る連鎖が起こり得る。このとき適用前後のゾーン差分だけを見ると、例えば**トラッシュが1枚のケースではデッキ枚数の増減が相殺**して「トラッシュ→場」に見え、IDを維持すべき「トラッシュから場への直接プレイ」と区別できず、デッキ経由を検出できない。よってサーバーは `Engine.setTrace(true)`（`engine.js:65`）を有効化し、`apply`/リプレイが返すトレース（`log` 1行ごとの全状態スナップショット。`engine.js:71`）を用いる。これはエンジンの**ロジックを変更せず**（既存の `TRACE` 機能を有効化するだけ。「エンジンは聖域」の原則を保つ）、非公開ゾーンへの流入ops（`shuffleTrashIntoDeck`（`engine.js:1068`→`log` は `1070`）・デッキ再構成（`engine.js:588`→`log` は `590`）等はゾーン設定直後に `log` するためスナップショットに必ず捕捉される）を漏れなく捉える。検出と加算の規則:
  - **遷移は隣接状態の比較で検出する**: 「適用の基準状態 → 各スナップショット → 当該applyの到達状態（中断時は中断時点の状態、完走時は最終状態）」の列を順に比較し、カードの `zone` が**別の値からデッキまたはいずれかの手札へ変わった瞬間**を「非公開ゾーンへの進入」として数える（デッキ→手札のドロー、手札→相手手札の移動（`engine.js:907`）も進入に数える）。**単にデッキ・手札に滞在しているだけのカードは対象外** — 滞在を対象にすると全デッキ・手札カードのIDが毎アクション更新され、自手札IDの安定性（クライアントの操作参照・UI継続性）が壊れる。
  - **choose再実行による重複を除外する**: エンジンの選択応答は保留中アクションを途中から継続せず、**基準状態から選択列を付けて再実行する**（`engine.js:1852`-`1860`: `runReplay(pend.base, pend.action, pend.choices.concat(...))`）。そのため最初の選択要求までに起きた遷移は、後続の `choose` 応答ごとのトレースに再登場する。そこで**論理アクション**（保留連鎖を開始した非chooseのエンジンアクション。そのログ行の `seq` で識別し、後続の choose 応答行はこれに従属する）ごとにカードUID別の**適用済み進入回数**を保持し、各applyのトレースで数えた進入回数との**差分だけ**をエポックへ加算する。エンジンは決定的（乱数は状態内で管理）で再実行は同一プレフィックスの遷移列を再生するため、差分は新規の遷移のみになる。「(論理アクション, カードUID) につき一度だけ」ではなく**回数の差分**とするのは、同一論理アクション内で同じカードが非公開ゾーンへ2度入るケースで2度目の進入にも新IDを与えるため（一度だけでは2つの裏向き登場が同一IDで結ばれ追跡を許す）。
  - **加算はビュー射影の前に行う**: 中断時のビュー（`engine.js:1843` の `view`）にも、その時点までの進入で更新した新IDを反映する。以後、同一論理アクションの choose 応答で当該カードのIDは変化しない（重複加算されないことの外形的な保証）。

  旧「保守的規則（公開領域からの退出を一括+1）」および「トレース中に存在したら+1（滞在検出）」は、この遷移直接検出により不要となり採用しない（トラッシュ→場の同一適用連鎖も、デッキ経由の実遷移として正しく検出される）。

  逆に、その場での表裏反転や、非公開ゾーンを一切経由しない公開領域内の遷移（場→トラッシュ等）ではIDを変えない（公開情報の連続性はUI演出にも使う）。エポックは両閲覧者で共通とする（上記の対称な規則で追跡不能性が満たせるため、閲覧者別の対応表・射影分岐は持たない）。
- **エポックはDBに保存しない**: 更新規則（隣接状態比較による遷移検出と、論理アクション単位の適用済み進入回数による重複除外 — 上記）は決定的なトレースだけから決まり、**稼働中も再起動後のリプレイ復元（3.1）も同一のapply列（元アクション + 各choose応答行）に対して同一のトレースを走査し同一の差分加算を行う**ため、同じカードには常に同一エポック＝同一公開IDが割り当たる（再起動をまたいでも公開IDは不変。稼働中とリプレイで異なるIDが生成されることはない）。**この不変性はエポック計算・射影コードが変わらないことが前提**であり、変更を含むデプロイの扱いは本節末尾のセッション互換ハッシュが定める。ゆえに永続化は不要で、リプレイ過程で決定的に再計算できる。導出時に稼働中IDとの衝突を検査し、万一衝突したら決定的なサフィックス付きで再導出する（リプレイでも同一結果になる。128bitで衝突は実質起きないが検査は安価）。**トレース捕捉の保証**: 非公開ゾーンへ入って同一アクション内に出るすべての経路が少なくとも1スナップショットに現れることを§8のテストで保証する（将来 `log` を挟まず非公開ゾーンを通過するopを追加した場合は、スナップショット点の追加かエポックのDB永続化で補う）。
- クライアント→サーバーのアクションは公開IDで受け、サーバー側で**現在エポックの対応表**（メモリ保持）で内部UIDへ逆引きする。エポック更新前の古いIDは解決しない（再送の冪等判定はID解決を要しないフィンガープリント比較で行う — 3.3）。
- **ID露出の不変条件**: デッキ内・相手手札内にあるカードのIDは、ビュー・選択候補・公開ログのいずれにも露出させない。現エンジンの選択候補は手札・場・トラッシュ由来のみでデッキ由来の候補は存在しない。手札・デッキトップの公開（reveal系効果）を公開ログで表現する場合は**カード定義のみを載せIDを付けない**（IDを付けると手札・デッキへ戻った後の追跡を許す）。§8の漏えい検査テストで保証する。
- **セッション互換ハッシュ（エポック計算・射影の変更をデプロイ跨ぎで無害化する）**: `ruleset_version`（3.1）が対象とするのはルール実行コードとカードデータのみで、エポック計算・トレースの解釈・逆引き対応表・ビュー射影のコードは対象外。これらを変更して通常デプロイすると、再起動後のリプレイ再計算が**同じログから異なるエポック**を割り当てうる。単なるID不一致（未適用再送の解決不能）にとどまらず、変更内容によっては公開IDが**過去に公開済みの値へ回帰**して追跡を許す（例: ある遷移でエポックを増やさなくする変更をすると、トラッシュ時代に両者へ公開されたIDと同一IDで裏向き再登場しうる）。対策として、**エポック計算・逆引き・公開射影を実装するモジュール群を1ディレクトリへ集約し（ハッシュ境界を構造で固定する）、`packages/protocol` と合わせた内容ハッシュ = セッション互換ハッシュ**をビルド時に自動導出して、公開IDのHMAC入力へ混ぜる（上記導出式）。帰結:
  1. これらのコードが不変の再起動では、公開IDは完全に同一（本節の不変性保証はそのまま成立）
  2. 変更を含むデプロイでは**全公開IDが一斉に無関係な新値へ回転**するため、過去IDへの回帰による追跡漏えいが**構造的に起きない**（すべての新IDはデプロイ前のどの観測とも結び付かない。位置による物理追跡は元々許容範囲 — 本節冒頭）
  3. 旧IDを含む未適用の再送は解決されず拒否される（fail-closed。クライアントは再接続時の最新ビューで再同期 — 3.5。適用済みアクションの冪等再送はフィンガープリント判定（3.3）でID非依存のため影響なし）

  ハッシュ値のDB保存・照合は不要 — 公開IDはセッション内の一時的なハンドルであり、常に現行プロセスの値だけで導出でき、不一致の「検出」をしなくても上記2/3が安全側に成立する。なお `log` スナップショットの位置などトレースの**生成側**はエンジンコードであり、そちらの変更は `ruleset_version` + ドレイン（§6）が扱う。

### 3.3 整合性・直列化・冪等性

メモリ状態とDBログの二重管理で起こる不整合を防ぐため、以下を仕様とする。

- **単一appプロセスに限定**する（本アプリの規模ではスケールアウト不要。将来複数プロセス化する場合はルームアフィニティの導入が前提となることを明記しておく）。
- **ルーム単位の直列化**: 各ルームにコマンドキューを持ち、**ルーム・ゲーム状態を変更するすべての処理**を1つずつ順に処理する。エンジンアクション・選択応答・タイマー発火（3.6）に限らず、接続attach・切断による切断期限の設定/解除（3.5）、対戦中の `room:leave`（投了を含む）、プロトコル選択・ドラフト操作・ゲーム開始・再戦、TTLクリーンアップ（ルームごとの閉鎖処理を該当ルームのキューへ投入）も対象で、**キューを経由しないルーム状態の変更を禁止する**。これにより「最終Socketの切断処理と再接続処理が競合し、再接続済みプレイヤーに切断期限が書き込まれて不戦敗になる」類の競合を排除する。同一バージョンのメッセージが並行到着しても後着は必ずバージョン不一致で拒否される。
- **処理順序**: (1) エンジン適用（メモリ上の複製で実行）→ (2) 同一DBトランザクションで `game_actions` 追記 + `games`/`rooms` 更新（終局時の `status`/`winner`/`end_reason` 確定も同一トランザクション）→ (3) コミット成功後にメモリ状態を確定しビューを配信。コミット失敗時はメモリ状態を破棄し、DBログからのリプレイで復元する。
- **一意制約**: `game_actions` に `UNIQUE(game_id, seq)`。直列化の破れがあってもDBが二重適用を最終防衛する。
- **冪等性（再起動をまたいで保証）**: クライアントは `game:action`・`game:choose` の**両方**に `actionId`（UUID）を付与。`game_actions` に `action_id`・`actor`・正規化後payload・**送信payloadフィンガープリント**（クライアント送信payloadをキー辞書順で正規化したJSONのSHA-256）・適用後 `version` を永続化し、`UNIQUE(game_id, action_id)` を張る。再送の同一性判定は `actor` + フィンガープリントの一致で行う — 公開IDは可視性エポック（3.2）で変わりうるため、古い公開IDを含む再送payloadを現在の対応表で正規化し直す方式は成立しない。正規化後payload（内部UID）はリプレイ用。メモリ上の処理済みキャッシュは高速化手段にすぎず正はDBとする。
- **受信処理の順序を固定**: ACK消失後の再送はクライアントのviewバージョンが必ず古くなっているため、バージョン検査を先に行うと成功済みアクションを「version不一致」で誤拒否する。同様に、終局手・投了の適用でゲームが終了すると `rooms.active_game_id` はNULLへ戻るため、gameId検査を先に行うと終局アクションの再送を `STALE_GAME` で誤拒否し冪等性が破れる。よって次の順とする:
  1. 送信者が受信 `gameId` のゲーム参加者であることを `games` の参加者列で検証。非参加者は拒否
  2. `(gameId, actionId)` で既存ログを検索。存在すれば `actor`・送信payloadフィンガープリントの一致を確認し、**ゲームが終了済みであっても成功済みとしてACK**する。`latestView` は `ruleset_version` が現行と一致するゲームに限りリプレイで再構成して返し、ruleset不一致の旧ゲームでは省略して `games` 行の結果（`status`/`winner`/`end_reason`）を `result` として返す（ACK型の `latestView` はオプショナル — 3.4）。不一致なら不正としてエラー
  3. ログが存在しない場合のみ、受信 `gameId` と `rooms.active_game_id` の一致を検査し、不一致なら `STALE_GAME` として拒否（3.4のgameId検証）
  4. viewバージョンと合法性を検査し、通常の適用処理（上記「処理順序」）へ
- **現在バージョンの正はログ**: ゲームの現在バージョンは `games` に重複保持せず、`game_actions` の最新行（`MAX(seq)`）の `version` から導出する（実行中はメモリ上のセッションが保持し、復元時はリプレイ結果と突き合わせる）。
- **ログは2種別（`kind` 列で区別）**: エンジンに渡していないpayloadを保存しない。
  - `kind='engine_action'`: payloadは公開IDを内部UIDへ逆引きし合法性を検証した後の「エンジンへ実際に渡した正規化済みアクション」（`surrender` の `player` もサーバー確定値）。リプレイヤーはこの種別**のみ**を `Engine.apply()` へ渡す。
  - `kind='game_terminated'`: エンジンアクションで表現できない終了（void等）のドメインイベント。payloadは `{ reason, 裁定に使った期限の種別・時刻 }`。エンジンには渡さず、対戦メタ状態（`games` 行）の終了に使う。
- **ゲーム開始も単一トランザクション**: 最終ドラフト結果の確定・`games` 行の作成（`game_config`・`card_id_secret` を含む）・`rooms.active_game_id` 設定・`rooms.status` 更新を1つのDBトランザクションで行う。ただし条件付き更新（`active_game_id IS NULL` のときのみ設定）**だけ**では二重作成を防げない: 再実行時に先に `games` 行を挿入した後で条件付き更新が0件になると、未使用のゲーム行が残る（この孤児は `status='in_progress'` のため再起動時の復元対象（3.1）に誤って拾われ、進行不能なゲームとして復元されうる）。よってトランザクション内で次を厳守する:
  1. `rooms` 行を `SELECT ... FOR UPDATE` でロックする（並行開始・再実行を直列化）
  2. `active_game_id` とドラフト完了状態を確認し、**未開始の場合のみ** `games` 行を作成する（既に開始済みなら作成せず、既存 `active_game_id` を冪等な結果として返す）
  3. `active_game_id` の条件付き更新が0件なら**トランザクション全体を必ずロールバック**する（孤児 `games` 行を残さない）

  さらに構造的な保証として、`games` に開始識別列（`room_id` + 再戦連番 `rematch_seq`）と **`UNIQUE(room_id, rematch_seq)`** を設け、同一ルーム・同一再戦回のゲーム二重作成をDB制約でも弾く（再実行が競合しても2行目の挿入が制約違反で失敗し、上記(3)のロールバックへ落ちる）。

### 3.4 Socket.IOイベント設計

| 方向 | イベント | 内容 |
|---|---|---|
| C→S | `lobby:list` | 公開ルーム一覧取得 |
| C→S | `room:create` / `room:join` / `room:leave` | ルーム操作（コード入室・パスワード対応） |
| C→S | `room:selectProtocols` | `{ roomId, version, protocols }` — 非ドラフト時のプロトコル3つ選択（両者完了で自動的にゲーム開始 = 現行 `protocols` op踏襲） |
| C→S | `draft:pick` | `{ roomId, version, step, picks }` — ドラフト選択（現行 `draftpick` op移植。最終ステップの確定でゲーム開始 — 3.3の単一トランザクション） |
| C→S | `room:rematch` | `{ roomId, version }` — 決着後の再戦。ルームをプロトコル選択（ドラフト設定時はドラフト）へ戻す。両参加者の在室が条件 |
| C→S | `game:action` | `{ gameId, actionId, expectedVersion, action }` — エンジンアクション（play/refresh/compile等） |
| C→S | `game:choose` | `{ gameId, actionId, expectedVersion, requestId, picks }` — エンジンrequest（選択要求）への応答。`requestId` は応答対象の選択要求ID |
| C→S | `chat:send` | チャット |
| S→C | `room:state` | ルーム状態（`roomId`・`version`・参加者・ステータス・**直近終了ゲームの結果**（`latestResult?: { gameId, status, winner, endReason }`。決着を受信できなかった再接続側のため — 3.5。**受信者が当該ゲームの参加者である場合にのみ含める受信者別フィールド** — 入れ替わりで入室した新ゲスト等の第三者へ過去の対戦結果を公開しない）。push配信） |
| S→C | `game:view` | 隠蔽済みゲームビュー（`gameId`・バージョン付き、push配信） |
| S→C | `game:log` | `{ gameId, entries: PublicGameLogEntry[] }` — 公開射影済みの行動ログ（下記） |
| S→C | `presence` | 相手の切断・再接続通知（`roomId` 付き） |
| S→C | `chat:message` | チャット（`roomId` 付き） |

- **ACK契約**: `game:action` / `game:choose` はSocket.IOのacknowledgementコールバックで応答する。応答型は `{ ok: boolean, appliedVersion?: number, errorCode?: string, latestView?: BoardView, result?: { status, winner, endReason } }` として `packages/protocol` に型定義し、成功・冪等再送・バージョン不一致・不正操作をクライアントが機械的に区別できるようにする。`latestView` がオプショナルなのは、ruleset不一致の旧ゲームへの冪等ACKでは現行コードでビューを再構成できないため（3.3の受信順序2）。
- **ルーム操作のACKと再送規律**: `room:create` / `room:join` / `room:leave` / `room:rematch` / `room:selectProtocols` / `draft:pick` もACKコールバックで `{ ok, errorCode?, ... }` を返すが、`game:action` と異なり**自動再送を禁止**する（`actionId` による冪等化を持たないため。ACK消失時はエラー表示とし、再接続時にサーバーがpushする最新 `room:state` で再同期する）。`room:create` の二重実行は `room_members` の `UNIQUE(user_id)`（4.2）が構造的に防ぐ。`room:selectProtocols` / `draft:pick` / `room:rematch` は `rooms.version` の楽観ロック（現行踏襲）で競合を検出し、不一致は `errorCode='VERSION_CONFLICT'` + 最新ルーム状態で応答する。
- **push配信の宛先識別**: S→Cイベントには対象の `roomId` / `gameId` を必ず含め、クライアントは自分が現在参加中のルーム・ゲームと一致しないpushを破棄する（再戦直後に届く旧ゲーム宛pushの誤描画防止）。1ユーザー同時1ルーム（4.2）のため、宛先のルーム・ゲームは常に高々1つに定まる。
- **クライアントプロトコル版数のハンドシェイク（デプロイ跨ぎの互換性）**: Socket.IOイベント形・`BoardView` 形は `packages/protocol` が定める。`ruleset_version`（3.1）は**ゲームルールの互換性のみ**を扱い、この通信プロトコルの互換性は保証しない。デプロイでプロトコルを変更すると、既に開かれている旧JSのブラウザが新サーバーへ再接続して操作不能になり、切断猶予（3.5）超過で不戦敗になり得る。対策として `PROTOCOL_VERSION` を**手動定数ではなく `packages/protocol` の内容ハッシュからビルド時に自動導出**し、server・webの両ビルドへ埋め込む — 手動版数には「スキーマを変えたのに版数更新を忘れ、旧クライアントがハンドシェイクを通過する」故障モードが残り、これは本書が `ruleset_version`（3.1）で手動定数を退けたのと同じ理由で受け入れない。版数の比較は完全一致のみで大小順序を使わないためハッシュで足りる。コメント等の無害な変更でも版数が変わるが、その代償は開いているタブの自動再読み込み1回で軽微。クライアントはこれをSocket.IOハンドシェイクの `auth` で送信し、**サーバーは完全一致のみ受理**する。不一致は専用エラー `errorCode='CLIENT_OUTDATED'` に**サーバー側の現行 `PROTOCOL_VERSION` を含めて**拒否し（「更新が必要」）、クライアントは受領時に自動でページを再読み込みして最新JSで復帰する（5節。再接続で進行中ゲームへ即復帰 — 3.5。自動再読み込みは**同一サーバー版数につき1回**に制限し、連続再読み込みループを防ぐ — 5節）。デプロイ手順側でも、Web資産の配信切替をSocket受付開始の直前に一括で行い、「再読み込みしても旧JSしか取得できない」期間を作らない（§6の起動バリア段4）。**旧版の受理（版数別互換層）は行わない** — ハンドシェイクだけ通しても、以後の全イベントに版数別zodスキーマと双方向変換（C→S入力の現行形式への変換に加え、S→Cの `game:view`・`room:state` 等の旧形式への逆変換）を維持しない限り旧クライアントは操作できず、中途半端な受理はかえって操作不能を隠す。webとserverは同一コミットから同時デプロイされるモノレポであり、この変換層はYAGNI。**ハンドシェイク時の一致検査だけで網羅できる根拠**: 単一appプロセス（3.3）でデプロイは必ずプロセス再起動を伴うため、プロトコル変更をまたいで生存するSocket接続は存在せず、旧クライアントは必ずハンドシェイク経路を通る。デプロイ跨ぎの救済（再読み込み→復帰の所要時間の扱い）は§6。
- **gameId検証**: 受信した `gameId` が `rooms.active_game_id` と一致しない場合は `errorCode='STALE_GAME'` として拒否する。同一ルームで再戦した直後に、旧ゲーム宛の保留・再送メッセージが新ゲームの操作として適用されるのを防ぐ。ただし3.3の受信順序のとおり、既存ログに該当する冪等再送はこの検査より先に成功済みACKで応答する（適用は起きない）。
- **選択応答の `requestId`**: エンジンは choose 応答に現在の選択要求IDとの一致を要求する（`engine.js` の `apply` が `action.id !== pending.requestId` を拒否）。`game:view` の選択要求に `requestId` を含めて配信し、クライアントは応答対象の `requestId` を `game:choose` で送り返す。リプレイ用に保存する正規化後payloadは「エンジンへ実際に渡した `{ type: 'choose', id: requestId, picks(内部UID) }`」。再送の冪等判定は送信payloadのフィンガープリント（3.3）で行うため、成功後に選択要求が先へ進み、可視性エポック（3.2）で公開IDが変わっていても成立する。
- **`game:log` は公開射影**: DBの `game_actions.payload` は内部UIDを含むリプレイ用データであり、**そのままクライアントへ配信してはならない**（内部UIDは `p{side}:{カード定義ID}` 形式のためカード定義が漏れ、3.2の不透明ID設計が無効になる）。S→Cのログは `packages/protocol` に `PublicGameLogEntry` 型を定義し、カード参照を公開IDへ変換し非公開情報を除外した**内部ログとは別の射影**とする（現行Edge Functionが盤面トレースのUIDを公開IDへ変換しているのと同じ規律）。公開IDを付けられるのは、その時点でID露出が許されるゾーン（ライン上・トラッシュ・自分の手札）にあるカードのみで、デッキ内・相手手札内のカードへの言及（reveal系効果・デッキトップ公開）はカード定義のみで表現する（3.2のID露出不変条件）。送信データに内部UID・`card_id_secret`・非公開カード定義が含まれないことは漏えい検査テストで保証する（§8）。

### 3.5 再接続・切断処理

- Socket.IO接続時にCookieセッションを検証し、進行中ゲーム（`rooms.active_game_id`）があれば最新ビューを再送して即復帰（1ユーザー同時1ルームのため復帰先は高々1つに定まる — 4.2）。
- **決着直後に切断していたプレイヤーの結果復元**: 進行中ゲームが無くても `rooms.latest_game_id` が指す直近ゲームを検索し、**再接続ユーザーがそのゲームの参加者（`games.player0_user_id` / `player1_user_id` のいずれかに一致）である場合に限り**、その結果（`status`/`winner`/`end_reason`）と最終ビューを返す。最終ビューは**必ず閲覧者本人のside用に射影**する（3.2の隠蔽射影。相手側視点のビューは返さない）。再構成は `ruleset_version` が現行と一致するゲームに限り、不一致の旧ゲームでは省略して結果のみ返す（3.3の受信順序(2)と同じ規律）。**非参加者には返さない**: ゲーム終了後にゲストが退出し別のユーザーが同じルームへ入れる（4.2: 待機中のゲスト退出は待機継続）ため、参加者判定なしに返すと過去の対戦情報（結果・最終盤面）を第三者へ公開してしまう。非参加者からの取得は拒否し、`room:state` の `latestResult` も**受信者ごとに**当該ゲームの参加者にのみ含める（3.4）。これにより、相手の操作でゲームが終了した瞬間に切断していて終了通知を受け取れなかった側も、再接続時に勝敗を受け取れる。
- attach・切断・再接続に伴う状態変更（切断期限の設定・解除を含む）はすべてルームキュー（3.3）内で処理する。
- 相手には `presence` で切断/復帰を通知。
- **切断判定は (ゲーム, ユーザー) 単位**: 当該ゲームに参加者としてattach済みの接続数をカウントし、その全attach接続が切れたときのみ切断扱いにする（複数タブの1つが閉じただけでは切断としない）。認証済み接続は進行中ゲームがあれば接続時に自動でattachされる（本節冒頭）。
- 切断猶予（60秒想定、設定可能）超過で不戦勝処理（システム投了。3.6のタイマー機構に載せる）。
- **切断猶予は通信断のみに適用**: 対戦中の明示的な `room:leave` は切断ではなく**即時投了**として扱う（4.2のライフサイクル参照）。

### 3.6 タイマー設計（新規設計）

現行Edge Functionにサーバー側タイマーは存在しない（現行のターンタイマーはクライアント側実装のみ）。したがってこれは移植ではなく新規設計である。

- **時間切れの効果は「システムによる投了」に統一する**。エンジンには `surrender` アクション（`action.player` 指定可）が既にあり、これを利用する。「強制refresh」や「選択要求への既定回答の自動送信」は選択が連鎖するケースの仕様が複雑になるため採用しない。
- **期限は絶対時刻で永続化**: 進行中ゲームに `deadline_at`（絶対時刻）と `deadline_holder`（現在の応答者 = 選択要求中はその回答者、通常時はターンプレイヤー）を保存する。プロセス内 `setTimeout` は起動中の発火手段にすぎず、正は常にDB。
- **切断猶予はターン期限と独立に管理**: 自分のターン期限が進行中に相手が切断するなど、2種の期限は同時に併存しうる。切断猶予はプレイヤー別の `disconnect_deadline_p0` / `disconnect_deadline_p1`（切断中のみ非NULL）で永続化し、ターン期限とは別のタイマーとして扱う。
- **更新条件**: 応答者が変わるたび（新しいターン、新しい選択要求の発生）に期限をリセットする。同一応答者への連続選択要求もリセット対象（1回答ごとに制限時間を与える）。
- **再起動時**: 進行中ゲームの期限3列（`deadline_at`・`disconnect_deadline_p0`・`disconnect_deadline_p1`）を**すべて**読み、タイマーを再登録する。復元時点で既に期限切れのものは、§6起動バリアの**段3（受付開始前の起動時裁定）**で、通常のタイマー発火経路（ルームキュー内の裁定）で処理する — 受付開始（段4）より前に裁定するため、再接続と裁定の競合は起きない。さらに、プロセス停止時にはdisconnectイベントを永続化できないため、**復元した全プレイヤーを一旦未接続として扱い**、切断期限が未設定のプレイヤーにも切断期限を設定する（Socket.IO再接続時に解除）。これを行わないと、ターンタイマー無効のゲームで再起動後に片方が戻らない場合、永久に進行不能になる。**再起動で新設・延長する切断期限の基準時刻は、プレイヤーが実際に再接続可能になる時刻（段4のSocket受付開始時刻）とする** — 復元時刻を基準にすると、復元・裁定に要した時間だけ再接続可能時間が短くなり、起動が遅いほど不当に不戦敗が増えるため。例外として、停止前から永続化されていて**復元時点で既に満了していた** disconnect 期限（＝実際に猶予を過ぎていた切断）は、猶予をリセットせず段3の裁定対象に含める。
- **タイマー発火時の再検証**: 発火待ちの間に期限が更新されるなど、`setTimeout` のコールバックは発火時点で古くなっている可能性がある。タイムアウト処理は必ずルームキュー内で実行し、投了を適用する前に (1) ゲームがまだ進行中、(2) DB上の期限が実際に満了済み、(3) `deadline_holder` が期待値と一致、(4) コールバックが保持する期限値（またはタイマー世代番号）がDBの現在値と一致 — を再検証し、満たさない古いコールバックは何もせず破棄する。再接続による切断期限解除と切断タイマー発火の競合も、同じ条件付き更新で扱う。
- **満了期限の裁定規則**: ターン期限と切断期限は種類をまたいで同時に満了しうる（例: P0のターン期限とP1の切断期限が、再起動やイベントループ遅延の後にまとめて期限切れになる）。タイマーごとに個別に投了処理すると勝者が実行順で変わるため、タイムアウト発火時はルームキュー内で**現在満了している全期限を収集**し、次の規則で裁定する:
  1. 最も早い期限の帰結を適用する
  2. 同時刻で敗者が同一プレイヤーなら、優先順位「切断 > ターン」で終了理由を確定する
  3. 同時刻で異なるプレイヤーが敗者となる場合は勝敗を付けず `status='void'`, `end_reason='simultaneous_timeout'` とする（再起動復元で両者に同一の切断期限が設定されるケース = 両者切断もここに帰着する）
  4. 裁定に使った期限の種別・時刻を終了イベントに記録する（下記「記録」）

  ルームキュー内で裁定するため、どのタイマーコールバックが先に処理されても結果は同じになる。
- **時刻精度と時刻源**: 期限3列（`deadline_at`・`disconnect_deadline_p0/p1`）はUTC・**ミリ秒精度（`DATETIME(3)`）**で保存する。秒精度では数百msずれた期限が同一値に丸められ、裁定規則の「同時刻」に誤って合致して `simultaneous_timeout`（void）になりうる。期限の生成・満了判定・裁定比較はappプロセスの時計に統一し（単一プロセス前提 — 3.3）、DB時刻関数（`NOW()` 等）を期限演算に混在させない。裁定規則の「同時刻」はミリ秒保存値の完全一致を指す。
- **記録**: タイムアウト・切断不戦勝は正規化済み `surrender` エンジンアクション（`kind='engine_action'`, `actor='system'`）として記録し、リプレイで同じ結果を再現する。voidなどエンジンアクションで表現できない終了は `kind='game_terminated'` のドメインイベント（3.3・4.2参照）として記録し、裁定に使った期限の種別・時刻を含める。
- ターンタイマー自体は現行同様ルーム設定で有効/無効を選べる（切断猶予は常時有効）。

### 3.7 バリデーション

- 全C→SメッセージはzodスキーマでValidate（`packages/protocol` に定義、web側でも型を共有）。
- 合法手チェックはエンジンAPIで実施（現行Edge Function踏襲）。
- レート制限: 接続数・メッセージ頻度の簡易ガード（現行 `room_abuse_guard` 相当）。
- **受信サイズの上限（頻度制限では防げない単発巨大メッセージへの対策）**: zod検証の時点でデータは既にメモリへ読み込まれているため、その手前のバイト数で頭打ちにする。単一appプロセス（3.3）では1件の巨大ペイロードが全ゲームに影響するため多層で設ける:
  1. Socket.IOの **`maxHttpBufferSize` を明示設定**（既定1MBに任せず**64KB**程度。正当なメッセージは最大でも数KB）。バイト上限はJSONのネスト深さも同時に制限し、パーサ例外は接続エラーとして扱う
  2. Fastifyの **`bodyLimit`**（64KB程度）と、Caddy側の `/api` 本文サイズ上限（§6。多層防御）
  3. zodスキーマの**全フィールドに個別上限** — 文字列は `.max()` 必須（チャット500字・ルーム名/表示名50字・パスワード128字（argon2の計算コスト悪用対策）等）、配列は要素数上限（`picks` はエンジンが提示する選択候補数に基づく小さな上限）
  4. 上限超過は不正入力として**接続を切断**し、IP・ユーザーIDを監査ログへ記録する（レート制限違反と同じ扱い）

## 4. 認証・DB設計

### 4.1 認証

- ユーザー名 + パスワード（argon2idハッシュ）。メール認証なし（メールサーバー不要に保つ）。
- サーバーサイドセッション: HTTPオンリー・Secure・SameSite=LaxのCookieにセッションIDを格納、実体は `sessions` テーブル。
- Socket.IOハンドシェイク時に同一Cookieセッションを検証。
- REST: `POST /api/auth/register` / `POST /api/auth/login` / `POST /api/auth/logout` / `GET /api/me`。

セキュリティ要件（Cookie属性 + zodだけでは不足するため明記）:

- **Origin検証**: Socket.IOハンドシェイクとREST更新系の両方で、許可Originの厳密な一致チェック（環境変数の許可リスト。現行Edge Functionの `ALLOWED_ORIGINS` 方式を踏襲）。
- **CSRF対策**: REST更新系はカスタムヘッダー必須化（`X-Requested-With` 等の存在チェック + Origin検証の併用）。SameSite=Laxは防御の一層にすぎない扱いとする。
- **セッション管理**: ログイン成功時にセッションIDをローテーション。DBにはセッションIDそのものではなく**そのハッシュ**を保存。期限切れセッションの定期削除、ユーザーによる全端末ログアウトAPIを用意。
- **Socket接続とセッションの連動**: 認証をハンドシェイク時だけで終わらせない。Socket接続を `sessionId`/`userId` 単位で管理し、(1) ログアウト時は当該セッションの接続を、全端末ログアウト時はそのユーザーの全接続を**即時切断**する。(2) セッション期限切れは定期検査（数分間隔）+ 重要イベント（`game:action`/`game:choose` 等）処理時の再検証で検出し、失効済みなら操作を拒否して切断する。確立済みSocketがセッション失効後も使い続けられる状態を作らない。
- **レート制限**: ログイン・登録・ルームパスワード試行・チャットにIP別 + ユーザー別の制限（現行 `room_abuse_guard` 相当をアプリ内ミドルウェアで実装）。
- **XSS**: チャット・表示名・ルーム名は常にテキストとして描画（Reactの既定エスケープに任せ、`dangerouslySetInnerHTML` は使用禁止）。

### 4.2 テーブル（Drizzle / MySQL）

| テーブル | 主な列 | 用途 |
|---|---|---|
| `users` | id, username(unique), password_hash, display_name, created_at | アカウント |
| `sessions` | id, token_hash, user_id, expires_at | サーバーサイドセッション（トークンはハッシュで保存） |
| `rooms` | id, code(unique), title, host_user_id, **guest_user_id**, status, visibility, password_digest, settings(JSON: ターンタイマー等), **draft_state(JSON)**, **active_game_id**, **latest_game_id**（直近に終了したゲーム。NULL可・FK。終了時に active_game_id と入れ替えで設定 — 3.5の結果復元用）, **version**（プロトコル選択・ドラフト操作の楽観ロック。現行踏襲）, created_at, **updated_at**（TTL判定の基準） | ルーム（side対応: host=player0 / guest=player1 で固定） |
| `room_members` | room_id(FK), user_id — **UNIQUE(user_id)** | 同時参加制約（1ユーザー同時1ルームのトランザクション保証。入室で挿入・退出/閉鎖/TTL掃除で削除） |
| `games` | id, **room_id(NULL可・FK `ON DELETE SET NULL`)**, **rematch_seq**（ルーム内の再戦連番。開始の冪等キー — 3.3）, player0_user_id, player1_user_id, **status**, winner(NULL可), **end_reason**, **game_config(JSON)**, **ruleset_version**, **card_id_secret**, **deadline_at**, **deadline_holder**, **disconnect_deadline_p0**, **disconnect_deadline_p1**, started_at, ended_at — **UNIQUE(room_id, rematch_seq)**（ゲーム二重作成をDBで防止 — 3.3） | 対戦記録（戦績の源泉 + リプレイ初期条件 + タイマー正データ） |
| `game_actions` | id, game_id, seq, **kind(engine_action/game_terminated)**, actor(player0/1/system), action_id(クライアント採番UUID。systemはNULL), payload(JSON: 種別ごとの内容は3.3参照), **payload_fingerprint**(送信payloadの正規化ハッシュ — 3.3。systemはNULL), version(適用後), created_at — **UNIQUE(game_id, seq)**, **UNIQUE(game_id, action_id)** | アクションログ（リプレイ・復元・冪等性判定用） |

- **プレイヤー表記は `player0` / `player1` で統一**: host=player0 / guest=player1。DB列（`player0_user_id`・`disconnect_deadline_p0` 等）、`game_actions.actor`、`deadline_holder` の値をすべて同一表記にする。例外は `game_config` 内の `p0`/`p1` キーのみで、これは `Engine.newGame()` の引数名の記録としてそのまま保存する。
- **1ユーザー同時1ルーム**: `room:create` / `room:join` は `room_members` への行挿入と同一トランザクションで行い、`UNIQUE(user_id)` 違反は「別のルームに参加中」として拒否する。退出・閉鎖・TTL掃除では同一トランザクションで行を削除する。席の正は従来どおり `rooms.host_user_id` / `guest_user_id`（`room_members` は制約の機構）。これにより1ユーザーの進行中ゲームは高々1つになり、再接続時の復帰先（3.5）とpush配信の宛先（3.4）が一意に定まる。
- **時刻列はUTC・`DATETIME(3)`（ミリ秒精度）で統一**: 特に期限3列は同時刻裁定に使うため必須（3.6）。
- `game_config` は `Engine.newGame()` に渡した引数の完全な記録（プロトコル・seed・先手・useControl）。`ruleset_version` はルール実行コード + カード/効果データのハッシュ（3.1参照）。
- **待機・ドラフト状態も復元対象**: `draft_state`（ドラフトの現在ステップ・残りプール・各プレイヤーの選択。非ドラフト時のプロトコル選択状況も含む）と `guest_user_id` により、再起動後も待機中・ドラフト中のルームへ参加者を元の席へ戻せる。ルームの認可判定（参加者か・どちらのsideか）は常にDBの列に基づき、メモリ状態に依存しない。
- **1ルーム最大1進行中ゲーム**: `rooms.active_game_id` が進行中ゲームを一意に指す（MySQLは部分インデックスを持たないため、この列 + ルームキュー内の検査で保証する）。ゲーム終了時は終局と同一トランザクション（3.3の処理順序(2)）で `active_game_id` をNULLへ戻し、同時に `rooms.latest_game_id` へ当該ゲームIDを設定する。これにより、終局の瞬間に切断していて終了通知を受け取れなかったプレイヤーも、再接続時に直近ゲームの結果へ到達できる（3.5）。
- **ルームのライフサイクル**:
  - ホスト退出時はルームを閉鎖する（`status='closed'`。ホスト移譲はしない = YAGNI）
  - ドラフト開始後にどちらかが退出した場合もルーム閉鎖（2人の選択が絡むためドラフトの巻き戻しはしない）。待機中のゲスト退出は `guest_user_id` をNULLへ戻して待機継続
  - **対戦中の明示的な `room:leave` は即時投了**: 退出プレイヤーの正規化済み `surrender`（`kind='engine_action'`）として記録し、`end_reason='surrender'` で決着させる。切断猶予（3.5の60秒）は通信断にのみ適用し、明示退出には適用しない。投了決着後は通常の退出処理（ホスト退出なら閉鎖、ゲスト退出なら待機継続）に続く
  - 待機・ドラフト中ルームは `updated_at` から2時間のTTLで自動閉鎖（サーバー内の定期クリーンアップジョブ。現行 `cleanup_secure_rooms` 相当）
  - 閉鎖時に `code` をNULL化してルームコードを解放・再利用可能にする（MySQLのUNIQUEはNULLを複数許容）
  - `rooms` 行は閉鎖から一定期間（30日想定）後に物理削除してよい。`games`/`game_actions` は戦績・リプレイのため保持し、ルーム削除に追従して消さない。この両立のため `games.room_id` はNULL可・`ON DELETE SET NULL` とし、戦績・履歴表示は `rooms` に依存させない（必要な情報は `games`/`users` が持つ）
  - ロビー一覧に表示するのは `status='waiting'` かつ公開かつゲスト不在のルームのみ（現行踏襲）
- ゲームの終わり方は `status` + `end_reason` で明示的に区別する:
  - `status`: `in_progress` / `completed` / `void`
  - `end_reason`（終了時のみ）: `normal`（コンパイル勝利）/ `surrender` / `turn_timeout` / `disconnect` / `simultaneous_timeout`（複数期限の同時満了で異なるプレイヤーが同時に敗北条件。両者切断を含む。3.6の裁定規則参照）/ `ruleset_mismatch` / `restore_failed`（隔離ルームの管理操作によるvoid — §6）
  - `winner` は `void` および将来の引き分けでNULL
- 戦績APIは `games` の集計（勝敗数・対戦履歴）。**集計対象は `status = 'completed'` のみ**とし、`void` は除外する。レーティング用の列・テーブルは今回作らないが、`games` に必要情報（対戦者・勝敗・時刻）が揃うよう設計しておく。

## 5. フロントエンド設計（React）

- Vite + React + TypeScript。状態管理はzustand。
- **`GameBoard` を共有コンポーネント化**し、2つのモードで使用:
  - **CPU戦**: ブラウザ内でengineをローカル実行（現行と同じ。オフライン動作可）
  - **ルーム戦**: サーバーからの `game:view` を描画。アクションはSocket.IO送信
- `GameClient` インターフェース（local実装 / socket実装）で抽象化する。ただしCPU戦は完全なエンジン状態を持ち、ルーム戦は隠蔽済みビューしか持てないため、**`GameBoard` の入力は共通の `BoardView` 型に固定**する:
  - 状態→`BoardView` の射影関数（隠蔽・不透明ID化・可視性エポック管理を含む）を `packages/protocol` に置き、**サーバーのredact処理と `LocalGameClient` が同一の射影コードを使う**。
  - `LocalGameClient` も完全状態を直接渡さず、この射影を通した `BoardView` を `GameBoard` に渡す（CPU戦ではダミー秘密値で不透明IDを生成）。これにより盤面UIにモード分岐が生じない。
- CPU AIは `engine.js` 内の `Engine.ai`（評価関数・ミニマックス探索）として実装済みで、`packages/engine` にそのまま同梱される。auto-play.html内のAIコードはエンジンのインライン複製にすぎず、切り出し・移植作業は不要（UIは `Engine.ai.action` / `Engine.ai.answer` を呼ぶだけ）。現行の「engine.js / auto-play.html / supabase/_shared の3箇所同期」問題はモノレポ化で解消される。初期実装は現行同様メインスレッド実行とし、Web Worker化は性能問題が確認された場合のみ行う。
- 既存CSS・アニメーション・演出は可能な限り流用し、コンポーネント単位に分割。
- **プロトコル更新への追従**: `CLIENT_OUTDATED`（3.4）受領時は「更新が必要」を表示し、**ユーザー操作を待たず自動で**ページを再読み込みして最新JSへ移行、再接続で進行中ゲームへ即復帰する（3.5。手動操作待ちにすると再読み込みまでの時間が切断猶予を消費する）。**連続再読み込みの抑止**: エラーに含まれるサーバー版数（3.4）ごとに自動再読み込みは**1回**とし、実施済みの記録はsessionStorage等（同一タブでリロードをまたいで残る領域）に持つ。再読み込み後も同じサーバー版数で `CLIENT_OUTDATED` を受けた場合（キャッシュ不整合・配信切替の異常など§6の手順が破れたとき）は自動再読み込みを停止し、待機を挟んだ再接続の再試行と手動更新の案内に切り替える（無限リロードで切断猶予を浪費しない）。ビルド成果物はViteの**ハッシュ付きファイル名**で配信し、`index.html`（および `static/` の各HTML）には**長期キャッシュを設定しない**（`Cache-Control: no-cache` 等。再読み込みで確実に新しいJS参照を取得できるようにする）。
- 画面: ホーム / ログイン・登録 / ロビー（公開ルーム一覧）/ ルーム待機（ドラフト含む）/ 対戦盤面 / 戦績・履歴。

## 6. インフラ・デプロイ

- **Docker Compose** on VPS:
  - `caddy` — TLS自動取得（Let's Encrypt）。webのビルド成果物と `static/` を直接配信し、`/api` と `/socket.io` のみappへリバースプロキシ（`/api` にはリクエスト本文サイズ上限を設定 — 3.7の多層防御）
  - `app` — Node.jsサーバー（API + Socket.IO専用。静的配信はしない）。**ポートは外部公開せずDocker内部ネットワークのみ**に置く。FastifyのtrustProxyをCaddyに限定し、信頼できるプロキシ経由の `X-Forwarded-For` からのみ実IPを取得する（これを誤ると、IPレート制限で全員がCaddyのIPに見える、または外部から偽装されたヘッダーを信用する）
  - `mysql` — MySQL 8系、ボリューム永続化。ポートは外部公開しない
- **CI/CD**: GitHub Actions — push → lint/テスト → Dockerイメージビルド → VPSへSSHデプロイ。デプロイ手順は次の順序を固定する:
  1. 新イメージをpullし、**新Web資産（webビルド成果物 + `static/`）をコミットSHA付きのリリースディレクトリへ配置する — この時点ではまだ公開しない**（Caddyの配信先切替は起動バリア段4）。イメージタグとリリースディレクトリは同一コミットSHAで揃え（`latest` は使わない）、直前タグ・直前リリースを記録してロールバック可能にする。**直前リリースの資産は削除せず残す**（切替直前に取得された旧HTMLが参照するハッシュ付きアセットの参照切れ防止。ハッシュ付きファイル名は版間で衝突しない）
  2. **Drizzleマイグレーションをappの起動前に実行**（専用の一時コンテナで `drizzle-kit migrate`）。失敗したらデプロイ中断・旧イメージのまま。マイグレーションは**expand/contract方式に限定**する: 先行適用してよいのは旧・新appの双方と互換なスキーマ変更（列・テーブル・インデックスの追加等）のみ。列削除・型変更などの破壊的変更（contract）は、新版の安定稼働を確認した後の**別デプロイ**に分ける
  3. app起動 → **起動バリア（順序を厳密に固定した4段階。各段はバリアで、前段完了まで次段へ進まない）**:
     1. **復元**: 進行中ルーム・ゲームをDBからリプレイ復元し、メモリセッションとタイマー満了時刻を再構築する（読み取り主体。この段では取り消し不能な裁定書き込みを一切行わない）。
     2. **切替確定（keep/rollback判定）**: `/healthz`（生存・DB疎通）＋復元完了を合否基準とする。**ロールバック判定はこの段で行う** — 不合格なら直前タグへロールバック（手順2の制約でスキーマは旧appと互換、かつこの段までに取り消し不能な裁定書き込みが無いため、旧appでそのまま続行できる）。合格＝新appの採用を確定。
     3. **起動時裁定（書き込み）**: 採用確定後に、書き込みを伴う起動時裁定（復元時の期限切れタイムアウト処理・ruleset不一致のvoid化）をルームキュー（3.3）内で実行する。この時点でまだ**Socket.IOの受付を開始していない**ため、クライアントのメッセージ（再接続・操作）が裁定より先にキューへ入ることはなく、裁定と再接続の競合（例: 満了済みの切断期限が再接続で誤って解除される、既に満了した無効試合が続行される）が構造的に起きない。切断期限の(再)設定は次段(4)の受付開始時刻を基準にする（3.6）。**毒データ耐性 — 1ルームの失敗で全体を止めない**: 段3の冒頭で全対象ゲームの裁定判定を**書き込みなしで事前計算（dry-run）**し、例外を出したルームを隔離予定に記録する。裁定の書き込みはゲーム単位の単一トランザクション（通常の終局処理と同一経路）で行い、失敗したルームは1回だけ再試行、それでも失敗するルームは**隔離**（下記）して残りの裁定と起動を続行する。壊れたログや実装不具合が1件あっても、全利用者の受付開始（段4）は妨げられない。途中クラッシュで一部ルームだけ裁定済みになっても、再実行は冪等（裁定済み＝終了済みゲームは3.6の「まだ進行中」再検証で自然にスキップされる）。段1の復元失敗も同じ隔離で扱う。
     4. **Web資産切替 → 受付開始**: 裁定完了後、まず**Caddyの配信先を新Web資産へ一括切替**する（リリースディレクトリを指すシンボリックリンクの張り替えなど、原子的に反映できる方法に限る。ファイル個別の上書きコピーは不可）。その後に **Socket.IOの受付を開始し `/readyz` を合格**にする。ここで初めてクライアントが再接続・操作できる。Socket受付と `/readyz` 合格はいずれも起動時裁定の完了後になる。**この順序が `CLIENT_OUTDATED` 再読み込みループを防ぐ**: 受付開始時点でWeb資産は必ず新版なので、「新サーバー受付中×旧JS配信」（再読み込みしても旧JSしか取得できず復帰不能・切断猶予を浪費）も「新JS配信×旧サーバー」も発生しない（3.4）。
     ロールバックの合否は段2（`/healthz`＋復元完了）で確定するため、段3以降で `/readyz` が遅れても旧appへは戻さず**新appを再起動**する（起動時裁定は終局済みゲームに対し冪等で、再実行しても結果は変わらない）。これにより「取り消し不能な裁定は採用確定後にのみ実行」と「Socket受付は裁定後」を両立する。**Web資産とappは常に同一コミットSHAで揃える**: 段2でロールバックする時点では資産は未切替（切替は段4）なので、旧資産×旧appで自動的に整合する。段4以降の失敗は新appの再起動で対処する（新資産×新app）。例外的に資産切替後へ手動でロールバックする場合は、appと同時に配信先リンクも直前リリースへ必ず戻す（片方だけ戻すと版数不一致の再読み込みループになる — 3.4）。
- **隔離（quarantine）ルームの扱い**: 復元（起動バリア段1）・起動時裁定（段3）で再試行後も失敗したルームは隔離状態とし、(1) Socket attach・ゲーム操作を専用エラー `errorCode='ROOM_QUARANTINED'` で拒否、(2) タイマーを登録しない（切断期限・ターン期限による自動敗北を進めない — 原因はサーバー側にあるため）、(3) ロビーに表示しない、(4) 監視アラート（ログ + 通知）で管理者へ知らせる。ゲーム行は `in_progress` のまま**管理者対応待ち**とし、修正版のデプロイによる再復元か、明示的な管理操作でのvoid化（`status='void'`, `end_reason='restore_failed'`）で解消する。**自動voidはしない** — 失敗の原因が実装不具合の場合、自動voidは多数のゲームを誤って無効化する取り消し不能な事故になる。最後の復旧手段として**保守モード起動**（環境変数で全ルームを隔離扱いにし、受付だけ開始する）を用意し、復元系の広範な不具合時も新規ゲームの提供と調査を並行できるようにする。
- **ルール挙動に影響する変更（ルール実行ファイルまたはカードデータの変更）を含むデプロイ**: `ruleset_version` が変わるため進行中ゲームは無効試合になる（3.1）。AI調整のみのデプロイは該当しない。該当デプロイは**進行中ゲーム0件を必須条件**とする: 新規ゲーム開始を一時停止（ドレイン）し、進行中ゲームの決着を待ってからデプロイする。待ちきれないゲームを打ち切る場合は、デプロイ前に**旧app稼働下で明示的な管理操作としてvoid**する — 新appの起動時void処理に委ねると、ヘルスチェック不合格→ロールバック時に取り消せない書き込みになる（3.1。起動時voidはドレイン漏れへの安全網であり、§6起動バリアの段3＝新app採用確定後・受付開始前にのみ実行される）。
- **通信プロトコルの変更を含むデプロイ**: 版数別の互換層は持たない（3.4）ため、旧クライアントは `CLIENT_OUTDATED` → 自動再読み込み → 新JSで再接続、が**正規の更新経路**である。デプロイは必ずapp再起動を伴い進行中ゲームの全プレイヤーに切断期限が新設されるが、その基準時刻はSocket受付開始時刻（起動バリア段4 — 3.6）であり、受付開始前にWeb資産切替が完了している（同じく段4）ため再読み込みは**1回**・数秒で完了し、切断猶予（60秒想定 — 3.5）内に収まる。切断猶予を短縮する場合も、再読み込み所要時間を猶予に含めることを維持する。**再読み込み→自動復帰の経路自体が成立しない変更**（例: セッションCookie形式の変更、再接続・復元セマンティクスの非互換）は、ルール変更と同様に**進行中ゲーム0件のドレイン**（前項）を必須とする。配信面では webビルド成果物・`static/` ともハッシュ付きアセット参照とし、HTMLに長期キャッシュを設定しない（5節。再読み込みが確実に新JSを取得できることが本経路の前提）。
- **バックアップ**: mysqldump日次cron + ローテーションに加え、**暗号化（age等）して外部ストレージへ転送**（VPS障害に耐えるため）。四半期に一度、バックアップからのリストア試験を行う。
- シークレット（DBパスワード等）は `.env`（gitignore）+ GitHub Actions Secrets。

## 8. テスト戦略

- **engine**: 既存 `test/engine.test.js` をVitestへそのまま移設（挙動保証の要。エンジン本体はAI節の分離に伴う変更 — 内部APIエクスポートの追加と依存性注入（§2設計原則）— 以外無変更であり、全テストが通ることが分離の等価性検証を兼ねる）。加えて**ゴールデンテスト**を追加: 代表的な初期条件 + アクション列 + 最終状態ハッシュを固定して保持し、意図しないルール挙動の変化をCIで検出できるようにする（`ruleset_version` はルール実行コードのハッシュから自動導出されるため更新漏れは構造的に起きない。ゴールデンテストはその挙動レベルの安全網。3.1参照）
- **server**: socket.io-clientを使った結合テスト — 2クライアントでルーム作成→ドラフト→対戦→決着までの主要フロー、不正アクション拒否、再接続復帰。加えて整合性まわりを重点的に: 同一バージョンの並行アクション（片方のみ受理）、`actionId` 再送の冪等性（**再起動をまたぐ再送を含む**）、**終局手・投了それぞれで「コミット成功後にACK消失→再送」が終了済みゲームに対しても成功ACKになること**、**成功後に選択要求が先へ進んだ状態での `game:choose` 再送が冪等成功すること**、タイムアウト発火、期限更新後の古いタイマーコールバックが破棄されること、再起動後のリプレイ復元・タイマー再登録・全プレイヤー未接続扱いからの切断期限設定、複数期限の同時満了の裁定（両者切断、およびターン期限×相手切断期限の異種競合がタイマー実行順に依らず同一結果になること、同時刻で敗者が分かれる場合は `void`/`simultaneous_timeout` になること）、再戦後の旧ゲーム宛の遅延メッセージのうち**未適用のものが `STALE_GAME` で拒否され、適用済みのものが冪等成功ACKになること**、対戦中の明示的 `room:leave` が即時投了として決着すること、ログアウト・全端末ログアウト・セッション期限切れ後の既存Socket操作の拒否と切断、不透明カードIDの検証（同一エポック内で安定・ゲーム間で無相関・カード定義から導出不能）、**可視性エポックの追跡不能性（トラッシュ→デッキ再構成→裏向き再登場、公開領域→手札→裏向きプレイ、の各経路で公開IDが変わること。特に**トラッシュ1枚での「トラッシュ→デッキ（シャッフル）→デッキトップから場へ裏向きプレイ」（前後差分ではトラッシュ→場と区別できないケース）でも公開IDが変わること**、ゾーン遷移トレースが非公開ゾーン経由を漏れなく捕捉すること、**単に手札・デッキに滞在しているだけのカードのIDがアクションを跨いで変化しないこと**、**複数の選択要求を含むアクションで、最初の選択前に手札へ入ったカードの新IDが中断時ビューに反映され、後続の選択応答（choose再実行）で変化しない＝重複加算されないこと**。リプレイ復元後もエポック再計算（重複除外を含む）が**稼働中と同一の**公開IDを与えること）**、**S→C送信データの漏えい検査（`game:view`・`game:log` 等の全ペイロードに内部UID・`card_id_secret`・非公開カード定義が含まれず、デッキ内・相手手札内カードのIDが露出しないこと）**、別ルームへの二重 `room:create`/`room:join` の拒否、`draft:pick`・`room:selectProtocols` のバージョン競合検出と `room:state` による再同期、**起動バリアの段階順序（keep/rollback判定→起動時裁定→受付開始の順で、Socket受付・`/readyz` 合格が起動時裁定より後になること、裁定前にクライアント操作・再接続がキューに入らないこと、再起動で新設する切断期限が受付開始時刻を基準にすること — §6/3.6）**、ruleset不一致の終了済みゲームへの再送が `latestView` なし（`result` 付き）の成功ACKになること、**決着を受信できなかった側の再接続（相手の操作でゲーム終了→直後に切断していたプレイヤーが、再接続時に `rooms.latest_game_id` 経由で結果と本人side用に射影された最終ビューを、`room:state.latestResult` で結果を受け取れること。あわせて、終了後に入れ替わりで入室した新ゲスト＝直近ゲームの非参加者には `latestResult`・最終ビューが返らず取得が拒否されること）**、**ゲーム開始の冪等性（`SELECT ... FOR UPDATE` 下で再実行・並行開始しても `games` 行が二重作成されず孤児が残らないこと、条件付き更新0件でトランザクションがロールバックされること、`UNIQUE(room_id, rematch_seq)` が二重作成を弾くこと）**、**プロトコル版数ハンドシェイク（不一致 `PROTOCOL_VERSION` のハンドシェイクが**サーバー版数付きの** `CLIENT_OUTDATED` で拒否されること、および拒否→クライアント自動再読み込み→新版で再接続→進行中ゲームへ復帰し以後の対戦操作が通ること、までの全経路。webテストでは**同一サーバー版数に対する自動再読み込みが1回で打ち止めになり、待機付き再試行と手動更新案内へ移行すること**）**、**起動時裁定の毒データ隔離（1ルームの復元・裁定失敗が隔離され他ルームの受付開始を妨げないこと、隔離ルームへの接続・操作が `ROOM_QUARANTINED` で拒否されタイマーが進まないこと、一部ルームのみ裁定済みの状態からの再実行が冪等なこと）**、**セッション互換ハッシュ（同一ハッシュでの再起動は公開IDが不変、ハッシュを変えた再起動では全公開IDが変わり旧IDを含む未適用再送が拒否されること＝fail-closed）**、**受信サイズ上限（`maxHttpBufferSize`・zod個別上限の超過メッセージが切断＋監査ログ記録になること）**
- **web**: GameClient抽象のユニットテスト + 主要コンポーネントのレンダリングテスト
- **E2E**: Playwrightで「2ブラウザでルーム対戦1ゲーム完走」スモーク
